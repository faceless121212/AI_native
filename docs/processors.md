## Sources and independent controllers (not processors)

- **Apple (Sign in with Apple, iOS)** and **Google (Google Sign-In)** are independent controllers for the sign-in itself, not our processors: the user has an account with them and they send us an identity. From Apple we receive the Apple user ID and an email (or private relay address), requesting the email scope only; from Google the Google user ID and email, with no extra scopes. Any name or avatar they still send is stripped (spec §10). Apple's refresh token is stored encrypted only so it can be revoked on deletion. Confirm the roles with counsel; mention both in the privacy notice.

## SMTP provider for auth emails (user to pick)

Needed for email confirmation and password reset in production. Options, all with EU sending:
- **Amazon SES** in `eu-central-1` (AWS DPA already needed for Bedrock).
- **Scaleway Transactional Email** (French company, EU-only).
- **Brevo** (French company).

Whichever is picked: open and click tracking off, SPF, DKIM and DMARC set on the sending domain, transactional templates only (no marketing lists).

## Supabase notes

- **Region:** both hosted projects must be created in **Frankfurt (eu-central-1)**. The local stack (`supabase start`) runs in Docker and is used with `LLM_MODE=fake` only.
- **What the client can read:** with Row Level Security, a signed-in user reads only their own rows in `profiles`, `consents`, `entitlements`, `usage_days`, `credit_ledger` and their own `referrals` codes. `ai_requests`, `reply_events`, `device_keys`, `support_messages`, `provider_status` and the `daily_cost` view are closed to clients; only Edge Functions (service role) use them. The `anon` role reads nothing.
- **No message content:** `ai_requests`, `ai_requests_daily` and `reply_events` have no text column; every text-typed column there is restricted by a check constraint to a fixed code list or short identifier pattern.
- **Retention jobs:** pg_cron runs `public.run_retention(now())` daily at 03:15 UTC. It folds `ai_requests` older than 90 days into `ai_requests_daily` (per UTC day, kind, source, language, provider, model, prompt version, status; **no user ID**) and deletes them in the same statement; deletes `usage_days` older than 90 days, and `reply_events` and `support_messages` older than 12 months; folds `credit_ledger` spend/refund rows older than 90 days into one `rollup` row per user and bucket (balances unchanged, no per-reply history kept); and deletes **inactive accounts**: auth users with no sign-in or session activity, no AI request and no device-key use for 12 months, with all their rows (cascade), except users with an active annual subscription (trial included; lifetime was removed on 2026-11-13). `daily_cost` reads both raw and aggregated rows, so cost totals survive the purge. Deleting auth users from SQL works for the `postgres` role that runs pg_cron locally; **confirm on hosted Supabase** (the documented way is the Auth admin API `deleteUser`; switch the job to an Edge Function if SQL deletion is refused there).
- **Consent versions:** the server accepts AI consent only for policy versions listed in `supabase/functions/_shared/policy.ts`; a minimum version is enforced in the SQL gate (`ai_allowed`), so raising it turns AI off until the user consents to the new text.
- **Device keys:** only the SHA-256 of the key is stored. Withdrawing AI consent revokes all of the user's keys in the same transaction.
- **Deletion:** every user table references `profiles` / `auth.users` with `on delete cascade`, so deleting the auth user removes the user's rows, consent records included (decided: consents are deleted with the account; spec §10 wording is the user's to update).
- **Auth:** anonymous sign-in on first launch. Decided 2026-11-13 (`docs/decisions.md`): after the paywall the user may sign in with Apple (iOS), Google or email + password, linked to the same user ID. Supabase Auth then holds the email, the Apple / Google identity and (email sign-in) a password hash, until account deletion (spec §10). Email sign-up stays off in `supabase/config.toml` until Prompt 8b builds it. No phone number is collected.
- **`reply` (Prompt 3):** holds the message text in memory only. It never logs it (a test runs every pipeline path with a marker text and fails if any log line, stored row or analytics event contains it) and never stores it. Per request it writes to `ai_requests`: kind, source, chip choices, language, provider, model, prompt version, tokens, cost, latency, status, number and indexes of the cards sent, safety flags (`refused`, `redacted`, `card_dropped`, `flirt_forced_off`; **not `crisis`**; crisis is only counted anonymously in `crisis_daily`), and the quota charge (`charge`, `charge_date`, `refunded_at`). Rows still `started` after 5 minutes are refunded and marked `abandoned` by a pg_cron sweeper. Free users' credit use adds a `spend` (−1) row to `credit_ledger` per credit-funded reply and a `refund` (+1) row when a failed reply is refunded, both linked by request ID with the bucket (starter or bonus) they came from, and folded into one rollup row per user and bucket after 90 days (decided). Edge Function logs get only codes and counts (status, provider, model, latency, tokens, cost, drop/redaction counts, and per dropped or changed card a reason code: `card_dropped` with `empty`, `too_long`, `explicit`, `banned`, `wrong_lang`, `same_opener` or `duplicate`, `card_fixed` with `emoji`); no user ID, no text, and nothing about why a request was refused.
- **`provider_status`:** provider failure counters and `down_until` (circuit breaker). No personal data.
- **While `anthropic` is the provider (staging), two promises are not true:** the onboarding line that chats are "processed in the EU", and spec §10 "sent to the AI provider with no retention" (Anthropic's standard and flagged-content retention apply until confirmed otherwise). So staging is for the team only, with synthetic chats, until a staging-specific consent text exists. Production can't use `anthropic` at all (no override).
- **Provider SDK hardening:** the Anthropic and Bedrock SDK clients run with logging off and fixed base URLs; staging and production refuse to start if environment variables that would redirect requests, add credentials or headers, or log/trace request content are set (`ANTHROPIC_LOG`, `ANTHROPIC_BASE_URL`, `ANTHROPIC_BEDROCK_BASE_URL`, `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_CUSTOM_HEADERS`, `ANTHROPIC_OPEN_TELEMETRY*`, …).
- **Region:** in production `reply` refuses (503) unless it runs in `eu-central-1`, read from `SB_REGION` (set by Supabase's hosted Edge Runtime; confirm on the first production deploy).
- **Crisis signal:** a deterministic phrase check backs up the model's crisis flag for the client's crisis card. Per user, nothing is stored, logged or sent to analytics (`ai_requests` can't store `crisis`). The only record is the anonymous `crisis_daily` table: a count per UTC day, language and source, with no user or request ID (decided).
- **Minor check:** a deterministic, in-memory check of the redacted copied message (`_shared/minor.ts`) looks for a first-person statement of an age under 18 or a minor's school year, in all five languages (spec §9). For a reply to a match or partner it refuses before any model call (refunded, as above), unless the crisis check matched (then the model answers supportively, with the crisis card). For any other reply it forces Flirty → Warm and flirt Off and stores `flirt_forced_off`, the same flag as the existing chip rules. The check's result, the age and the matched words are never logged, stored or sent to analytics; nothing is sent to a provider for a refused request.
- **"I am" / "They are"** stay on the phone (decided): sent with each reply request for the prompt, never stored on the server; `profiles` has no such columns.
- **Starter credits** (+10) are granted when the anonymous account is created (decided: "on install"); using them still needs AI consent and 18+.
- **Refusals** with no card shown are refunded (decided). A refusal made on the server before the model (minor check, below) is stored like a model refusal (status `refused`, flag `refused`, language), but after the refund its `relationship`, `tone` and `flirt` are set to NULL, so the row can't be read as "this user's match said they're a minor". Charge, refund time and creation time stay (refund and rate limit need them).
- **Analytics:** `safety_flag` events (refused, redacted, …) are anonymous aggregates without a user ID (sink is a no-op until Prompt 13).

## Open questions (for the user / counsel; not changed in code)

1. **Supabase transfer mechanism and platform log retention:** confirm SCCs / DPF, the sub-processor list, log fields and retention for the chosen plan (see the Supabase row).
2. **Anthropic (direct API) is not an EU processor:** development and staging only, team members with synthetic chats. Production uses Bedrock (EU profile) and/or Mistral; the code has no override. Confirm Anthropic's transfer mechanism (SCCs/DPF), DPA acceptance, standard and flagged-content retention, and zero-data-retention availability; write a staging consent text before anyone outside the team tests staging.
3. **Provider retention settings before launch:** Bedrock model invocation logging off and the account's data-retention mode; Mistral zero data retention in writing.
4. **Automated safety checks on the other person's message (minor check):** the server derives from someone else's message whether they appear to be under 18 and acts on it (refusal, or no flirting). Confirm with counsel the lawful basis for this processing and for the derived record (a `refused` row, or a `flirt_forced_off` flag, linked to the pseudonymous user ID for 90 days; whether Art. 10 or special-category rules can apply to such inferences, and whether clearing the chips on refused rows is enough), and add it to the DPIA and to the privacy-notice text on automated safety checks (what is checked, what happens, what is kept).

Decided (Prompt 3, by the user): consent rows are deleted with the account (cascade); crisis is counted only anonymously (`crisis_daily`); inactive anonymous accounts are deleted after 12 months (except paid; lifetime no longer exists since 2026-11-13); starter credits on install; credit spend rows folded after 90 days; "I am" / "They are" stay on the phone; refusals with no card shown are refunded; with no fallback provider the first-token wait is 5 s.
