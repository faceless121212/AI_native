## Supabase notes

- **Region:** both hosted projects must be created in **Frankfurt (eu-central-1)**. The local stack (`supabase start`) runs in Docker and is used with `LLM_MODE=fake` only.
- **What the client can read:** with Row Level Security, a signed-in user reads only their own rows in `profiles`, `consents`, `entitlements`, `usage_days`, `credit_ledger` and their own `referrals` codes. `ai_requests`, `reply_events`, `device_keys`, `support_messages`, `provider_status` and the `daily_cost` view are closed to clients; only Edge Functions (service role) use them. The `anon` role reads nothing.
- **No message content:** `ai_requests`, `ai_requests_daily` and `reply_events` have no text column; every text-typed column there is restricted by a check constraint to a fixed code list or short identifier pattern.
- **Retention jobs:** pg_cron runs `public.run_retention(now())` daily at 03:15 UTC. It folds `ai_requests` older than 90 days into `ai_requests_daily` (per UTC day, kind, source, language, provider, model, prompt version, status; **no user ID**) and deletes them in the same statement; deletes `usage_days` older than 90 days, and `reply_events` and `support_messages` older than 12 months. `daily_cost` reads both raw and aggregated rows, so cost totals survive the purge.
- **Consent versions:** the server accepts AI consent only for policy versions listed in `supabase/functions/_shared/policy.ts`; a minimum version is enforced in the SQL gate (`ai_allowed`), so raising it turns AI off until the user consents to the new text.
- **Device keys:** only the SHA-256 of the key is stored. Withdrawing AI consent revokes all of the user's keys in the same transaction.
- **Deletion:** every user table references `profiles` / `auth.users` with `on delete cascade`, so deleting the auth user removes the user's rows (see open questions).
- **Auth:** anonymous sign-in only; email sign-up is off. No email, phone or password is collected in v1.

## Open questions (for the user / counsel; not changed in code)

1. **Consent proof vs deletion:** spec §10 keeps consent records "until deletion + 3 years"; today `consents` cascade-delete with the account. Decide before Prompt 10 (Delete my data), e.g. keep a de-identified proof row.
2. **Per-user `crisis` safety flag:** `ai_requests.safety_flags` can hold `crisis` linked to a user ID for 90 days, which may be health-related (Art. 9) data. Decide whether to store it unlinked, only in the aggregate, or not at all (before Prompt 3 writes it).
3. **Orphaned anonymous accounts:** reinstalling creates a new anonymous user; the old one keeps its rows indefinitely. Decide an inactivity purge (e.g. no sign-in for N months) and add it to the retention job.
4. **Starter credits timing:** the spec says "10 starter replies on install"; the server grants them on first AI consent (no AI without consent anyway). Confirm the wording in the spec and store copy.
5. **Supabase transfer mechanism and platform log retention:** confirm SCCs / DPF, the sub-processor list, log fields and retention for the chosen plan (see the Supabase row).
